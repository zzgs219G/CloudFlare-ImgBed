# 历史修改记录

## 问题 1：CNB 渠道上传后，浏览器打开链接出现项目自带 404 页面

**日期**：2026-09-21
**状态**：已修复（代码已改，待部署 + 清缓存）

### 现象（用户实测）

- 用 CNB 渠道上传图片，拿到自定义链接（如 `https://img.614118.xyz/file/1789970676695_img3038.webp`）
- 用浏览器直接打开 → 出现项目自带的"精美 404 页面"
- 后台缩略图、预览图正常加载；后台"下载"按钮正常下载到图片
- 结论规律：**不用浏览器打开就正常，用浏览器打开就 404**

### 根因（curl 实测确认）

1. 普通 curl 请求 `/file/xxx.webp` → 正常 302 跳转到 CNB 直链，能拿到图片 ✅
2. 带浏览器特征头（`Sec-Fetch-Dest: document` 等）请求同一 URL → 直接返回 **`cf-cache-status: HIT` 的 `text/html`**（SPA 的 index.html），根本没回源到 Worker ❌

**结论**：Cloudflare 边缘缓存把一份 SPA 的 HTML 缓存到了 `/file/xxx.webp` 这个 URL 上（响应头标签 `cf-cache-status: HIT`、`Content-Type: text/html`）。浏览器导航请求命中这份脏缓存，前端路由里没有 `/file/` 页面，于是渲染出项目自带的 404 页面。

- 这就是以前 AI 说的"标签问题"：是响应头标签（缓存状态、Content-Type）把错误内容标记到了图片 URL 上，重新部署时缓存重新产生，问题就复现。
- 后台正常是因为：后台预览/下载走的请求路径和缓存变体不同，没有命中脏缓存。

### 修复方案（治本 + 兜底）

核心思路：**CNB 渠道对用户直接返回国内直链，浏览器不再经过 Cloudflare 的 `/file/` 路由**，脏缓存问题彻底绕开；`/file/` 路由保留作兜底（302 跳转 CNB 直链）。

改动 3 个文件：

| 文件 | 改动 |
|---|---|
| `CloudFlare-ImgBed/functions/upload/index.js` | `uploadFileToCnb` 成功后返回 `result.url`（CNB 直链），不再返回 `/file/` 链接；`cnbChannel.returnUrl === false` 时可回退旧格式 |
| `CloudFlare-ImgBed/functions/utils/metadata/metadataView.js` | 新增 `enrichCnbMetadata`：管理端列表接口透出 `CnbUrl` 直链字段 |
| `Sanyue-ImgHub/src/views/AdminDashBoard.vue` | `handleCopy` 新增 CNB 分支：复制链接时用 `metadata.CnbUrl` 直链（originUrl/mdUrl/htmlUrl/bbUrl 四种格式），缺失时回退 `rootUrl` |

### 验证结果

- `node --check` 两个后端文件通过
- `@vue/compiler-sfc` 编译检查 AdminDashBoard.vue 通过
- curl 复现边缘脏缓存命中（text/html）确认根因
- `git diff` 复查仅包含预期改动

### 部署后必须做的两件事

1. **Cloudflare 后台 → 缓存 → Purge Everything**：清掉 `/file/` 路径上的脏缓存，老图片的 `/file/` 兜底链接才能恢复正常 302 跳转
2. **Sanyue-ImgHub 重新 build**：后台"复制链接返回直链"要 build 后才生效（后端上传返回直链不依赖前端 build）

### 修复后的完整流程

```
上传（选 CNB 渠道）
  │
  ├─ POST /upload?uploadChannel=cnb
  ├─ 上传图片本体到 CNB（api.cnb.cool 三步上传）
  ├─ KV 写入记录：key = fullId（如 1789970676695_img3038.webp）
  │    metadata = { Channel: "CNB", CnbUrl: "https://cnb.cool/.../xxx.webp",
  │                 CnbFilePath: "/zzgs219/cdn-img/-/imgs/.../xxx.webp", FileName, FileType ... }
  └─ 接口直接返回 {"src": "https://cnb.cool/.../xxx.webp"} ← 国内直链 ✅

用户访问
  └─ 浏览器直接访问 CNB 直链（国内速度），不经过 Cloudflare ✅

后台管理
  ├─ 文件记录依旧按 fullId 存在 KV 里（缩略图/预览/下载/删除照旧）
  └─ 复制链接 → 复制出 CnbUrl 直链 ✅

兜底：/file/{id} 仍然可用
  └─ 302 跳转到 CnbUrl（需先 Purge 清掉脏缓存）
```

## 问题 2：CNB 删除一直失败（上传正常）

**日期**：2026-10-09
**状态**：已修复（提交：5205d97 → 4bfb3da → abe9538 → ff03eae，已验证成功）

### 现象

- 后台删除 CNB 渠道上传的文件返回 400「删除失败」
- 上传图片/文件完全正常
- CNB 平台侧文件从未被真正删除过

### 排查过程（三个叠加 bug，逐个暴露）

**第 1 轮：读错 KV key（提交 `5205d97`）**

```javascript
const settingsKV = await db.get('settings');  // ❌ 错误 key
```
上传配置实际存在 `manage@sysConfig@upload`。修复 key 后，日志里 `CNB channel config not found` 依旧。

**第 2 轮：删除路径格式错误（提交 `4bfb3da` → `abe9538`）**

- CNB swagger 实测：上传返回的 `assets.path` 形如 `/{slug}/-/assets/xxx/xxx/uuid.png`
- 删除接口要求传「访问链接中 `/-/imgs/` 或 `/-/files/` **之后**的相对路径」（如 `abc/123.png`）
- 原代码把完整 `assets.path` 直接拼进删除 URL → 路径重复
- 且 `encodeURIComponent` 会把 `/` 编码成 `%2F`，破坏路径
- 修复：新增 `extractDeletePath()` 剥离 `/-/assets/` 前缀（兼容 4 种历史格式），新增 `encodeAssetPath()` 按段编码

**第 3 轮（最终根因）：KV 读取后缺少 `JSON.parse`（提交 `ff03eae`）**

```javascript
// db.get() 返回原始 JSON 字符串，不是对象！
const settingsKV = await db.get('manage@sysConfig@upload');
settingsKV?.cnb?.channels  // ❌ 字符串取属性永远是 undefined → 找不到配置 → 删除必失败

// 上传代码（getUploadConfig）一直是对的：
const settingsStr = await db.get('manage@sysConfig@upload');
const settingsKV = settingsStr ? JSON.parse(settingsStr) : {};  // ✅ 有 parse
```

**这就是「上传正常、删除一直失败」的真正原因**——上传路径有 `JSON.parse`，删除路径没有。前两轮修复都是必要的，但这个 bug 一直掩盖在前两层之下，配置永远读不到，根本走不到删除请求那一步。

### 排查中的辅助手段

1. 修复了 `deleteFile` 不检查 `deleteCnbFile` 返回值的问题（提交 `740f1b3`）——之前 CNB 删失败也照样删库，造成「显示删除成功但 CNB 文件还在」的假象；现在失败会中止并报错
2. 增加详细日志：删除时输出完整请求 URL，失败时输出 CNB 的 HTTP 状态码和响应体
3. 用户多次提供 Workers 日志（docs/报错日志.md），最终靠完整日志（error + warn 同请求）定位到 `config not found` 复现

### 验证

修复后（`ff03eae` 部署后）用户实测：删除成功，CNB 平台侧文件同步删除 ✅

### 经验教训

1. **删配置和读配置必须用同一套代码路径**（本次删除单独写了一套读取逻辑，漏了 parse）
2. **对接第三方 API 先查官方 swagger，不要猜路径格式**（`assets.path` 的 `/-/assets/` 格式就是从 swagger 确认的）
3. **权限差异要留意**：CNB 上传（`repo-code:rw`/`repo-notes:rw`）和删除（`repo-manage:rw`）权限不同，token 需同时勾选
4. **错误要如实暴露**：之前删除失败仍删库返回成功，掩盖了问题两年；修复后失败立即中止，问题才浮出水面

### 关联修复（同期）

1. **构建报错**：`uploadFileToCnb` 符号冲突（本地函数与导入重名）→ 重命名本地函数为 `uploadFileToCnbChannel`（提交：da45595）
2. **删除不检查返回值**：CNB 删除失败仍删库 → 现在检查返回值，失败阻止数据库删除并打印详细日志（提交：740f1b3）
3. **前端新增上传模式下拉框**：后台 CNB 渠道配置新增 `uploadMode` 选项（自动识别/强制图片接口/强制文件接口）
